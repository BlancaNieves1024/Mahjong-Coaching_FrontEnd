### 1. 報告すべき技術仕様（コードのアーキテクチャ）

開発した仕組みの意図と設計思想について説明します。

* **データ処理の分離**
* 抽出（`extract.py`）と可視化（`main.py`）の処理を分離。将来的なバックエンドの実装（API化）を見据えた柔軟な構造にしています。


* **JSON連携の標準化**
* 中間ファイルとして `data.json` を介する形式を採用。バックエンド完成時のAPI統合を容易にする設計です。


* **テンプレートエンジンの採用**
* `Jinja2` を活用し、Pythonのデータを直接HTMLへレンダリング。JavaScriptによる複雑なDOM操作を排除し、レンダリング速度とメンテナンス性を向上させました。


* **牌コードの正規化**
* システム内部の牌コード（`4m`等）と、UI表示用の牌記号（Unicode/日本語）を分離し、表示のカスタマイズ性を確保しています。

* **Flaskによるサーバーサイドレンダリング構成**
* プロジェクト構成を app.py と templates/（index.html / template.html）に整理し、Python（Flask）を軸にしたシンプルなMVCライクな構造を採用。

* **関心事の分離（データ処理と可視化の連携）**
* app.py 側で入力されたURLを受け取り、バックエンドの解析結果を想定したデータ処理・牌コードの正規化（Unicode変換）を行った上で、テンプレートへ引き渡すフローを構築。


* **Jinja2テンプレートを活用した動的UI**
* JavaScriptによる複雑なDOM操作を排除し、Jinja2のテンプレート構文（{% for %} など）を用いて、変換された麻雀牌や解析結果（ロス値など）を綺麗に描画。


* **フロントエンド側でのURLバリデーション**
* 入力画面（index.html）のJavaScriptにて、空欄チェックや https:// の有無、天鳳・雀魂のドメイン判定を行う早期リターン型のバリデーションを実装し、不正なリクエストを事前にブロック。



### 2. バックエンドチームに連携すべき内容

今後の開発に向けた仕様のすり合わせ事項です。

* **将来的なAPI連携インターフェースの調整**
  * 現在はフォーム送信による画面遷移（POST）で検証を行っているが、将来的にはREST APIのJSONレスポンスを直接受け取る構成への移行を見据えたインターフェースの相談。

1. フォーム送信による画面遷移（POST）方式
バックエンドでHTMLを生成してそのまま返す、今回のプロトタイプで採用したサーバーサイドレンダリング的なアプローチです。

メリット
* **実装が非常にシンプル**: JavaScriptでの複雑な非同期処理（`fetch` やDOM操作）を書く必要がなく、コード量が少なくて済む。
* **エラーハンドリングが楽**: 通信失敗時やバリデーションエラー時の画面遷移・再描画をブラウザ標準の動きに任せられる。
* **初期表示が高速（データが整った状態で届く）**: サーバー側でHTMLを完成させて返すため、クライアント側での描画待ちが発生しにくい。

デメリット
* **画面全体のリロードが発生**: 送信ボタンを押した際に一瞬画面が白くなったり、ページ全体の再読み込みが挟まるため、モダンなWebアプリのような滑らかさに欠ける。
* **「解析中...」などのローディング演出が難しい**: サーバーの処理が終わるまで次の画面に切り替わらないため、アニメーション等のリッチなUXを実装しにくい。

2. REST APIによるJSONレスポンス方式（非同期 / SPA的アプローチ）
JavaScriptからAPIを叩き、返ってきたJSONデータをもとに動的に画面を書き換える（または別画面へデータを引き渡して描画する）アプローチです。

メリット
* **リッチでスムーズなUX**: ページ全体のリロードがなく、ローディング中に「解析中アニメーション」を挟むなど、操作感が非常にモダンで快適になる。
* **役割分担が明確**: バックエンドは「純粋なデータ（JSON）の返却」に専任し、フロントエンドは「UIの描画」に専任できるため、将来的なReact等への移行が圧倒的にスムーズ。
* **将来の拡張性が高い**: 画面だけでなく、将来的にスマホアプリや他のクライアントへ展開する際も同じAPIをそのまま流用できる。

デメリット
* **実装コストが高め**: JavaScriptの非同期処理（`async/await`）や、エラー時のフォールバック、動的なDOM書き換えのコードを自分で書く必要がある。
* **初期の結合テストの手間**: ブラウザのデベロッパーツールなどでCORS（クロスドメイン）やJSONの型不一致などをデバッグする手間が増える。
